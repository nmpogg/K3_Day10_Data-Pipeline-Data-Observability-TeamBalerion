## 4. Giải thích phần kỹ thuật đã thực hiện

### Vấn đề cần giải quyết

Làm thế nào để so sánh hiệu suất chính xác giữa Baseline và Repaired nếu mỗi lần chạy nó lại tự sinh câu hỏi ngẫu nhiên?
Làm thế nào để chấm điểm tự động các câu trả lời khi LLM trả về mà không bị dính fallback `NotImplementedError` của HuggingFace?

### Cách triển khai

Mình code hardcode cố định Test Set ra file JSON luôn (gồm 14 câu hỏi trải dài từ Factual, Summary, Date, Author) (Freeze Test Set).
Với `metrics.py`, sửa system prompt yêu cầu LLM "Mày phải trả ra JSON object có score và correct", sau đó dùng Regex và `json.loads` để parse kết quả từ string, vô hiệu hóa `.with_structured_output`.

## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** Bị crash lúc dùng HuggingFace LLM cho JudgeVerdict.
- **Các phương án đã cân nhắc:** Thay LLM OpenAI hoặc viết lại hàm parser.
- **Phương án đã chọn:** Tự viết JSON parser thủ công.
- **Lý do:** OpenAI tốn tiền và đôi khi bị rate limit, LLM local dù không support struct_output nhưng vẫn rất ngoan ngoãn sinh JSON nếu prompt kĩ.
- **Bằng chứng quyết định phù hợp:** Chấm điểm Accuracy phản ánh hoàn hảo 100% thay vì rớt vì khác vài từ do dùng Token F1.

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng/lỗi nguyên văn:** Markdown report không update dữ liệu mới.
- **Nguyên nhân gốc:** Code ở `reporting.py` không gọi hàm `generate_corruption_report` lúc run Phase 2.
- **Cách xử lý:** Bổ sung hàm call ở cuối Phase 2 Orchestration.
- **Cách xác minh sau khi sửa:** Check ngày giờ file modified.
- **Điều học được:** Automation cần phải liên kết tận răng.

## 7. Hiểu biết về luồng end-to-end

1. **Dữ liệu đi từ Crossref đến vector index như thế nào?** Data được fetch về, làm sạch, biến thành chunk nối text, đẩy qua BGE-Small để tạo Embeddings, lưu vào Chroma.
2. **Evaluation set và ground-truth document IDs dùng để đo retrieval/answer quality ra sao?** Retrieval tính hit-rate thông qua kiểm tra Doc ID trả về có khớp ID gốc không.
3. **Quality checks khác freshness monitoring ở điểm nào trong bài lab?** Quality (có đủ field không), Fresh (có mới không).
4. **Vì sao phải dùng cùng test set cho baseline, corrupted và repaired?** Để làm đối chứng (A/B Test Control Group).
5. **Repair được xem là thành công dựa trên artifact và metric nào?** Judge Score khôi phục lại 5.0.

## 8. Phân tích kết quả

### Metrics chính

| Metric/signal          | Baseline | Corrupted | Repaired | Nhận xét của cá nhân |
| ---------------------- | -------: | --------: | -------: | ------------------------- |
| `retrieval_hit_rate` |      1.0 |       0.833 |      1.0 | Observability hoàn thành nhiệm vụ cảnh báo |
| `mean_token_f1`      |      0.67 |       0.51 |      0.69 | F1 bị phá vỡ hoàn toàn |
| `judge_accuracy`     |      1.0 |     0.667 |      1.0 | Metrics rớt thê thảm do Rác nhiễu |
| `mean_judge_score`   |      5.0 |       3.67 |      5.0 | Phục hồi hoàn toàn |
| Quality checks         |      Pass |       Fail |      Pass | Cảnh báo Data drift tốt |
| Freshness status       |      Fresh |       Stale |      Fresh | Quá hạn 2000-01-01 bị bắt trúng |

### Kết luận từ số liệu

1. **Data corruption** → **Signal Fail** → **Hit Rate Giảm**.
2. **Repair action** → **Signal Pass** → **Metrics về mức 5.0**.

Sự cố hỏng Title làm Retriever hoàn toàn "mù" và giảm hit rate thẳng thừng. Rất hợp lý.
